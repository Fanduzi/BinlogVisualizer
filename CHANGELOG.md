# Changelog

This file records user-visible changes for tagged releases.

## [Unreleased]

### Added

- Version-matrix fixtures for MySQL 5.7.44, 8.4.11, 9.7.2 and MariaDB 10.11.19, 11.8.9: `analyze` is compared with each server's own `mysqlbinlog -vv` decode, and the flashback boundary (FULL undone, MINIMAL, DDL, missing row metadata and 11.8 generated columns refused) is tested (#366).
- `flashback` warns `mariadb_apply_unsupported` for a MariaDB binlog.

### Changed

- **Breaking for `analyze --format json`: `report_version` is 4 (#379).** `selection.matched_gtids`, one entry per matched transaction, is replaced by `selection.matched_gtid_set`, an interval set (MySQL `uuid:1-4:6-3000000` per server UUID; MariaDB `domain-server-seq` or `domain-server-first..last` per run of sequence numbers, per server, or shared by the servers that write one domain), and `selection.matched_transactions`, the number of matched transaction groups with at least one event in the time and position window, once per group read (a GTID read twice counts twice; a matched DDL group or a group cut by `--stop-position` before its first row counts too, so it can exceed `summary.total_transactions`). `--include-gtids` and `--exclude-gtids` accept MariaDB `d-s-first..last` ranges, so the set can be passed back and selects exactly the matched transactions (#381 QA F1, F2). Reports without GTID selectors change only in `report_version`. `compare` and `trend` read v3 and v4 reports. Before, every matched GTID stayed in memory until the report was written (117-375 bytes per match), so `--exclude-gtids` of one GTID on a 3M-transaction binlog ran out of memory with exit 2; memory now grows with the gaps between matched GTIDs, not with matches. `TestAnalyzeMatchedGTIDSetHeap` in CI covers 1,048,576 vs 262,144 matched transactions with a single-GTID exclude: 92MB more heap before, 13-20KB after (GOMAXPROCS 1 and 8).
- `analyze` and `flashback` with `--include-gtids`/`--exclude-gtids` exit 10 `resource`, `details.reason` `matched_gtid_intervals`, when the matched GTIDs need more than 100,000 separate intervals, instead of growing without bound (#379). The message is localized and gives the number of intervals needed, and `flashback --help` lists the reason. MariaDB servers that alternate in one domain no longer need one interval per transaction. Inserting GTIDs in descending order is no longer quadratic. `compare` and `trend` reject a negative `matched_transactions` as corrupt (exit 5).
- `docs/production-readiness.md`: E1 (bounded memory) is MET; 18 MET / 1 PARTIAL / 5 NOT MET, 6 of 24 remain.
- A flashback script stops on a MariaDB server at its first statements with ERROR 1231 `binlogviz: flashback apply does not support MariaDB; no rows were changed; ...` and changes nothing, also under `mysql --force`. It used to stop at an unrelated `ERROR 1064` while creating the finish procedure, or with `--force` roll back with `ERROR 1758`. The undo statements from a MariaDB binlog are exact; applying them on MariaDB is not supported.
- The missing-row-metadata refusal on a MariaDB binlog names MariaDB 10.5+ `binlog_row_metadata=FULL` (default `NO_LOG`) instead of MySQL 8.0.14.
- Scripts generated by v0.34.0 or earlier do not carry the MariaDB stop. They still pass `flashback verify` and fail safely on MariaDB the old way (`ERROR 1064`, or `ERROR 1758` with `--force`, no rows changed). Regenerate them with this version to get the clear ERROR 1231 stop.
- Analyze text, Markdown, JSON, and HTML now list the same key transactions: the `--top-transactions` ranking (`AnalysisResult.Transactions`). Text no longer substitutes a separate largest/longest/widest set, and HTML evidence no longer names a transaction outside that list. A listed transaction that is also one of those capped champions keeps the label (`Largest transaction`, `Longest transaction`, `Widest transaction`). `report_version` stays 3. JSON `transactions`, `transactions_listed`, and `transactions_omitted` are unchanged (#352, ADR 0012).
- `analyze` memory no longer grows with the number of transactions: per-table and per-minute transaction counts no longer keep a key set, the hot-row map is rebuilt so delete/insert churn cannot grow it, and the apply-delay P95 keeps at most 8192 values in memory and spills the rest to an unlinked temp file (about 8 bytes of temp disk per transaction; it falls back to memory if no temp file can be created). The exact nearest-rank P95 and all analyze output are byte-identical. `TestAnalyzeRetainedHeap` in CI asserts the peak live heap at 100k transactions stays within 256KiB of 25k (#364). If the spilled delays cannot be read back, `analyze` fails with `read spilled apply-delay values` instead of dropping the apply-delay section; `TestAnalyzerFailsWhenSpilledDelaysCannotBeRead` pins this.
- `analyze` and `flashback` with `--include-gtids` or `--exclude-gtids` no longer hold the open transaction in memory. Before, every event of the open transaction was buffered until it closed (about 4.3KB per event), so one transaction of 300k row events ran out of memory and crashed with exit 2. The include/exclude decision is now made from the GTID event that opens the transaction, and events stream through. Output is unchanged. `TestAnalyzeGTIDFilterRetainedHeap` in CI covers 100k vs 25k transactions under a filter and one 300k-event transaction (#376, `docs/gtid-filter-streaming.md`). The matched GTID evidence is bounded too (#379, above).

## v0.33.0

Release date: 2026-10-20

Highlights:

- **Breaking for flashback apply:** v0.32.0 scripts must be regenerated; `flashback verify` exits 6 with `details.reason` `old_format` (#342). Success is the anchored line `binlogviz: undo committed, N statements` (or `... with skips, N applied, M skipped`), not the `mysql` exit code.
- Apply grants on the undo tables are `SELECT, INSERT, UPDATE, DELETE` (#341). Under `PAD_CHAR_TO_FULL_LENGTH` and with `BINARY(n)` keys a keyed undo now matches; one that does not change exactly one row rolls back (#347, #348). A failed apply drops its procedure and prints the real error (#338, #343). Refusals carry `details.reason` (#344).
- `schema_version` 1, `plan_version` 2, `report_version` 3, and analyze output are unchanged.
- Known issue: Linux release archives still report an empty commit (#303).

Related notes:

- [v0.33.0 release notes](docs/releases/release-notes-v0.33.0.md)
- [v0.33.0 中文发行说明](docs/releases/release-notes-v0.33.0.zh-CN.md)

### Changed

- Flashback apply grants on the tables the undo changes are `SELECT, INSERT, UPDATE, DELETE`. v0.32.0 omitted `SELECT`; `UPDATE` and `DELETE ... WHERE` then fail with ERROR 1143 (#341).
- **Breaking:** a flashback script written by v0.32.0 must be regenerated. `flashback verify` exits 6 with `details.reason` `old_format` (#342).
- A failed apply drops the finish procedure it created. Success is `binlogviz: undo committed, N statements` when nothing was skipped, and `binlogviz: undo committed with skips, N applied, M skipped` otherwise. Exit 0 without the matching line is not success. A rolled-back apply prints `binlogviz: undo rolled back, no rows changed` and stderr shows the real errno and message (#338, #343, #347). A kill before the finish `CALL`, or a `CALL` that never enters, can still leave the procedure. `DROP DATABASE IF EXISTS binlogviz` needs `DROP` on `binlogviz.*`.
- `PAD_CHAR_TO_FULL_LENGTH` is removed before `CREATE PROCEDURE`, and a keyed `UPDATE` or `DELETE` undo that does not affect exactly one row rolls the apply back (#347). That includes a no-PK `LIMIT 1` match. The saved `sql_mode` is restored after the apply, including when it fails.
- `BINARY(n)` values in a flashback are padded to n bytes with `0x00`, in `WHERE`, `SET`, and `INSERT`. v0.32.0 wrote the short value, so a keyed undo matched 0 rows (#348). `VARBINARY`, `BLOB`, and `CHAR` are not padded.
- Success, when nothing was skipped, is a line matching `^binlogviz: undo committed, [0-9]+ statements$`. When some rows were skipped it is `^binlogviz: undo committed with skips, [0-9]+ applied, [0-9]+ skipped$`. The marker is `CONCAT` pieces, so the literal is not in the SQL. `mysql --force -v` echoes the statement, and a plain grep of that echo is not a commit. N counts undo statements that changed exactly one row. `--conflict guard` counts 1 row as applied, 0 rows as skipped, and any other count as a rollback. A no-PK `INSERT` undo under `--conflict guard` inserts only when that image is absent, so a second apply skips it. Control characters in a server message are replaced before the rollback line and the stderr copy, so a value cannot forge the commit line. MySQL 5.7 warning 3090 (a deprecated combination `sql_mode`) is not a failure. A published file applied without `verify` does not report `ERROR 0`; the no-commit trailer is the error. `--plan --sql-context off` reports `would_refuse` true with reason `sql_context_off` and exits 6. A stream cut after `COMMIT` leaves the undo committed with no marker.
- `flashback verify` reports an intact v0.31 or v0.32.0 script as `details.reason` `old_format` and says to regenerate it (#342).
- Flashback generation refusals set `details.reason` (`row_metadata`, `row_image`, `column_type`, `row_capture`, `ddl_in_range`, `generated_unknown`, `generated_mismatch`, `generated_row`, `schema_mismatch`, `sql_context_off`) and `details.table` when one table is named. A MySQL 5.7 binlog cannot be undone (#344).
- README exit codes match the CLI (corrupt input is exit 5, a flashback refusal is exit 6). `trend` keeps argument order unless `--order time` is set. `install.sh --help` prints usage (#345).

## v0.32.0

Release date: 2026-10-20

Highlights:

- **Breaking for flashback apply:** ADR 0014 (#332, #337). A failed apply never commits a prefix of the undo: the undo is one XA transaction, so script `BEGIN` / `START TRANSACTION` / DDL cannot commit it, and the finish commits only when every statement succeeded (#328, #329). v0.31.0 scripts do not verify; regenerate them.
- Apply needs `CREATE`, `CREATE ROUTINE`, `ALTER ROUTINE` on `binlogviz.*`, plus `EXECUTE` when `automatic_sp_privileges=0`; `XA_RECOVER_ADMIN` is not needed (#333). A failure before `XA START` stays recorded under `mysql --force`. Each run gets its own `SQL SECURITY INVOKER` finish procedure, so leftovers do not block (#334). `flashback verify --help` usage is fixed (#335). Clean leftovers with `DROP DATABASE IF EXISTS binlogviz`.
- `schema_version` 1, `plan_version` 2, `report_version` 3, and analyze output are unchanged.
- Known issues: some missing-grant paths leave the per-run finish procedure behind (#338); Linux release archives still report an empty commit (#303).

Related notes:

- [v0.32.0 release notes](docs/releases/release-notes-v0.32.0.md)
- [v0.32.0 中文发行说明](docs/releases/release-notes-v0.32.0.zh-CN.md)

### Breaking

- Flashback SQL from v0.31.0 does not verify. Regenerate it. Apply creates the `binlogviz` database if it is absent and a procedure in it, and needs `CREATE`, `CREATE ROUTINE`, and `ALTER ROUTINE` on `binlogviz.*`. The stock `mysql` client is required (`DELIMITER`). `schema_version` stays 1 and `plan_version` stays 2 (#328, #329, #333, ADR 0014).

### Fixed

- `binlogviz flashback verify | mysql --force` no longer commits a prefix of the undo when the target is missing a table or a column (#328). A truncated file followed by another script, `BEGIN`, `START TRANSACTION`, or DDL, and a complete file followed by those under `--force`, no longer commit the undo (#329). The undo is one XA transaction. The finish commits only when every statement succeeded. See ADR 0014.
- The XA apply grant on `binlogviz.*` is `CREATE`, `CREATE ROUTINE`, and `ALTER ROUTINE`. `DROP PROCEDURE IF EXISTS` needs `ALTER ROUTINE` even when the procedure does not exist (ERROR 1370). Under `mysql --force` that 1370 used to be wiped by the following `CREATE PROCEDURE`, and the undo committed; the failure now stays recorded, so a pre-XA error does not commit. `CREATE` on that schema covers `CREATE DATABASE IF NOT EXISTS binlogviz`. `XA RECOVER` is not used, so `XA_RECOVER_ADMIN` is not required. With `automatic_sp_privileges=0`, `CALL` also needs `EXECUTE` on `binlogviz.*`. The same grant works on MySQL 5.7 and 8.0 (#333, ADR 0014).
- `binlogviz flashback verify` gives each apply its own finish procedure, `binlogviz.binlogviz_fb_end_<token>_<nonce>`, and drops that procedure at the end. A leftover routine owned by a `SYSTEM_USER` account (ERROR 1227 on MySQL 8.0) does not block the next apply. MySQL 5.7 has no `SYSTEM_USER` privilege. Clean leftovers with `DROP DATABASE binlogviz`. New scripts create the procedure `SQL SECURITY INVOKER`. `schema_version` stays 1 and `plan_version` stays 2 (#334, ADR 0014).
- `binlogviz flashback verify --help` prints that command's usage. Sibling subcommands were already correct (#335).

## v0.31.0

Release date: 2026-10-20

Highlights:

- **Breaking for flashback apply:** ADR 0013 apply-time integrity (#318, #321). The published undo is one transaction that never commits by itself. `binlogviz flashback verify` checks the digest and emits the conditional `COMMIT`; apply with `binlogviz flashback verify file.sql | mysql`, not `mysql < file`. The SQL is the new sealed format, not byte-compatible with v0.30.0; `plan_version` stays 2.
- Partial, edited, reordered, appended, or truncated scripts are refused by `verify` with exit 6 and commit nothing. Generation exit 8 leaves no applyable prefix. Invalid `BINLOGVIZ_SPILL_BYTES` / `BINLOGVIZ_MEMORY_BYTES` are exit 3.
- `flashback verify` streams: RSS about 34–41 MB on 400 MB+ scripts; a heap ceiling is exit 10 `memory_limit` (#327).
- Known issues: `verify | mysql --force` can commit partial undo when the target lacks a table or column (#328); an implicit commit after a truncated or complete file can commit (#329); Linux release archives still report an empty commit (#303).

Related notes:

- [v0.31.0 release notes](docs/releases/release-notes-v0.31.0.md)
- [v0.31.0 中文发行说明](docs/releases/release-notes-v0.31.0.zh-CN.md)

### Breaking

- Applying a flashback script is a new command (ADR 0013, #318, #321). `mysql < flashback.sql` no longer changes data, including when the file is intact. Apply with `binlogviz flashback verify <file> | mysql --default-character-set=utf8mb4`. The undo is one transaction, not one per original transaction. The SQL is not byte-compatible with v0.30.0. `plan_version` stays 2.
- `BINLOGVIZ_SPILL_BYTES` and `BINLOGVIZ_MEMORY_BYTES`, when set, must be a positive base-10 integer. `abc`, `0`, `-1`, `1MB`, and empty are exit 3 before a binlog is read. Unset still means no spill ceiling, and the memory ceiling stays `GOMEMLIMIT`.

### Fixed

- `binlogviz flashback verify` hashes the undo while it reads and does not load the script into memory (#327). SQL output is emitted from a temp file after the digest matches. A heap ceiling is exit 10 (`memory_limit`). A full disk while writing that temp file is exit 8. Neither is exit 2.
- A flashback script commits nothing unless it is complete and unmodified (#318, #321, ADR 0013). Edited values, a deleted undo statement, reordered statements, appended SQL, and a truncated file are refused by `binlogviz flashback verify` (exit 6) and commit nothing under `mysql`, including `--force`. A token that does not match inside one statement is ERROR 1242, not a silent zero-row update. Generation writes the script to a temp file and copies it to stdout only after that write succeeds, so exit 8 does not leave a prefix that applies.
- `TestGeneratedReviewRSS` skips under `-race`. Its failure text says 64MB.

### Install

- **`install.sh` no longer fails silently or installs an unverified binary (#285).** A checksum mismatch now prints `checksum mismatch for <archive> (expected …, got …)` and an archive missing from `checksums.txt` prints `no checksum for <archive>`; both exit 1 and install nothing. The install-docs test now also rejects pinned `releases/download/vX.Y.Z/` URLs.

### Fixed

- **Real MySQL 8.0 compressed transactions of 16 MiB and up now parse (#278, #293).** With `binlog_transaction_compression=ON`, MySQL writes the uncompressed size of a payload of 16 MiB or more as a 9-byte field, which v0.24.0 refused with exit 5. Decompression is now streamed and bounded: each inner event is checked and released as it is decoded, a payload is handed to `analyze`/`flashback` only after it decodes cleanly (so a payload corrupt at its last event prints nothing and exits 5), and a payload may name at most 65536 distinct tables. On BinlogQA's runs a 33 KB zstd bomb and a 99 KB file declaring ~1 GiB of tiny events both exit 5 at about 30–44 MB peak memory; a 30 MB real MySQL 8.0.36 binlog parses at 95–160 MB. A valid ~1 GiB payload of tiny events takes about 45 s, because it is decompressed twice.
- A compressed transaction payload (`binlog_transaction_compression=ON`) that declares more than 1 GiB uncompressed now fails with a message like `payload declares 1.0 GiB (1073741825 bytes) uncompressed, more than the limit 1.0 GiB (1073741824 bytes)` instead of the misleading `payload header field exceeds the event` (#278). MySQL writes sizes of 2^24 and up as a 9-byte field, which the header check refused. Either way the parse stops with exit 5; only the message changes.

- **P2 (QA r2 on #290): `workflow clean --include-snapshots` trusted `manifest.snapshot_dir`.** Cleaning a restored export moved snapshots in the original snapshot dir, and a forged `snapshot_dir` could move files out of any directory. Clean now takes the snapshot dir only from the new `clean --snapshot-dir` flag or the default, and refuses with exit 6 (`snapshot_dir_mismatch`) when the manifest names a different one. `workflow export` writes `snapshot_dir` as the relative `snapshots`. A ledger snapshot entry must be recorded by its own step (`analyze:<name>` for `<name>.json`), else 5 `untrusted_ledger`.
- `workflow clean --apply` checks every trash target on both sides (artifacts and snapshots) before moving anything, so a refusal leaves nothing half-moved. Exit 8 now names each file and the cause, and clean JSON gains `skip_reasons`.
- The deletion guard test now covers `cmd/binlogviz`, `internal/workflow` and `internal/snapshot`, catches function-value and import aliases, `os.Root` methods and `os/exec`, and checks a reviewed allowlist.

- **P1 #289: `workflow clean` deleted the last good run's outputs and snapshots after a failed re-run.** A failed run rewrites the manifest, so clean's view no longer matched the disk. Clean now uses per-file attribution (ADR 0009 §8). `workflow run`/`resume` append every file they write (path, step, run id, sha256) to `<output_dir>/ledger.jsonl`, and clean deletes only ledger-recorded files whose sha256 still matches and that no current step owns. Everything else is kept and listed in `kept_orphans`; `--force` (new) also deletes unattributed outputs of recorded step kinds. Clean refuses with exit 6 when the latest run did not succeed (`run_not_successful`, not overridable). `--include-snapshots` deletes only snapshots the ledger attributes, never one the workflow did not create.
- **P1 (QA r5 on #290): `workflow clean` could delete files outside the workflow root.** A forged ledger snapshot entry (absolute or `snapshots/../` path with the right sha256) or a symlinked `analyze/`, `compare/` or `trend/` dir made clean delete through it with exit 0. All deletions now go through one primitive that takes the root plus a relative path, refuses `..`, absolute paths and symlinks at every component, and moves files to `<root>/.trash/<id>/` (snapshots: `<snapshot-dir>/.trash/<id>/`) instead of unlinking; clean never empties the trash. Ledger paths are relative only (snapshots are a bare `<name>.json`); anything else is 5 `untrusted_ledger`. A symlinked kind dir is 6 `trust_boundary`, even with `--force`. Symlinked files are never deleted. `workflow run`, `resume` and `clean` take an exclusive lock on `<root>/.lock` (6 `locked`). `workflow export` includes `ledger.jsonl`.
- **Migration:** workflow directories from earlier versions have no ledger, so clean refuses (6, `no_ledger`). Re-run `binlogviz workflow run <plan.yaml>` into the directory to rebuild it, or pass `--force` (it never deletes snapshots).
- Clean JSON gains `force`, `ledger` and `kept_orphans`; `snapshot_orphans` and deleted snapshot entries are snapshot file names relative to the snapshot dir; `--apply` adds `trash_dir` and `snapshot_trash_dir`. The manifest gains `run_id`.
- `workflow export`'s plan warning follows `--error-format json` (one `{"warning":{…}}` line).

- **P1: `workflow clean --apply` deleted every output when the manifest was untrustworthy.** A `{}` manifest, or one with `steps` missing or `[]`, made clean treat every analyze/compare/trend output as orphaned, delete them all and exit 0. Clean (preview and `--apply`) now refuses and deletes nothing: a manifest missing required fields exits 5, and one that records no steps while artifacts exist exits 6, both with `details.reason: untrusted_manifest`. Clean also only considers files of kinds the manifest recorded steps for (ADR 0009 §8).
- `workflow export` with a `{}` manifest exits 5 instead of writing an archive with only index.html and manifest.json. With no recorded steps it warns that artifacts are not included. When plan.yaml is not included it now warns on stderr too, and `--format json` reports `plan_included` (new field).

### Known limitations

Review a flashback script, test it, and apply it in a single session on the primary. A statement that fails leaves earlier transactions in the script committed. See `docs/concept/limitations.md`.

- [#166](https://github.com/Fanduzi/BinlogVisualizer/issues/166): a correct `--schema-file` is refused when a generated column uses an expression the checker cannot verify (JSON extraction, `UPPER`, `CONCAT`, `DIV`, and `/` when MySQL rounded the result). Omitting `--schema-file` still assigns that column, and apply stops at `ERROR 3105` with earlier transactions already committed. Pass the binlog that holds `CREATE TABLE` (or a later `ALTER`) and select the incident with `--include-gtids`, or delete the generated columns from the script. `--include-table` / `--exclude-table` only skips the table.
- [#167](https://github.com/Fanduzi/BinlogVisualizer/issues/167): an `ALTER` in the parsed binlog is applied a second time on top of a schema file that already contains it. The error lists the same column twice (`reordered (schema file ...; binlog ...)`, `id, a, b, c, c`). Use a dump taken before that `ALTER`, or leave out the binlog file that holds it. Joined dumps need `USE db;` before each one, or one flashback per database with `--schema-file-db` and that database's own dump file. A per-database run against the joined file refuses or warns and does not use the definition (fails safe, does not restore). An ambiguous name needs `USE` or a qualified table.
- [#168](https://github.com/Fanduzi/BinlogVisualizer/issues/168): restoring `ENUM` index 0 under `sql_mode=TRADITIONAL` fails with `ERROR 1265`. `SELECT @@SESSION.sql_mode` contains `TRADITIONAL`, and the script contains `@binlogviz_sql_mode`. Set the session to `STRICT_TRANS_TABLES,STRICT_ALL_TABLES,NO_ZERO_IN_DATE,NO_ZERO_DATE,ERROR_FOR_DIVISION_BY_ZERO,NO_ENGINE_SUBSTITUTION` (TRADITIONAL without the `TRADITIONAL` token). An outer transaction does not help: each original transaction has its own `START TRANSACTION`, which commits implicitly.
- Resuming after a failed apply: blocks above the failure are already committed, and blocks below it are not. The script is in reverse binlog order. Re-running the whole script duplicates rows in a table with no primary key (`ERROR 1062` on a primary key). Keep the header (`SET NAMES`, `SET time_zone = '+00:00'`, `SET SESSION sql_mode`, every line before the first `-- gtid:`), delete only the transaction blocks above the failed one, and run the header plus the failed block and everything after it in a new session. Without the header, `TIMESTAMP` values are restored shifted by the session time zone and apply still exits 0 (#173). The failed block is the last `-- gtid:` line at or before the line number in the client error. Do not re-run a transaction that already committed.
