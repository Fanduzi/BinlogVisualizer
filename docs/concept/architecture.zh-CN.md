# 产品架构

BinlogViz 通过单次流式处理管线分析本地 MySQL ROW binlog 文件。命令路径被设计为只顺序前进一次，在内存中保持有界的实时状态，并在解析完成后再组装最终报告。

## 高层流程

```text
binlog files -> parser -> normalize -> analyzer -> finalize -> renderer -> output
```

在命令层面，`binlogviz analyze` 会先解析输入路径、校验输入、构建分析器选项，然后执行这条从解析到报告的流式管线。

## 管线阶段

### 1. Parser

Parser 负责读取一个或多个本地 binlog 文件，并通过回调发出原始 binlog 事件。它既可以运行在显式文件模式下，也可以运行在 discovery 模式下：命令先根据 `--from-dir` 和 `--prefix` 解析出一个有序文件列表，再开始分析。

这一阶段负责读取 binlog 流，不负责构建最终的用户报告。

### 2. Normalize

原始 Parser 事件会先转换成稳定的内部事件结构，再进入分析阶段。这样分析器就不需要直接依赖 Parser 的细节，后续阶段也都可以基于一致的事件契约工作。

### 3. Analyzer

Analyzer 会在事件到达时立刻消费标准化事件。它会重建事务、更新负载汇总、跟踪表级和分钟级活动，并准备大事务和可选写入尖峰等告警输入。

这一阶段仍然属于流式路径：事件是增量消费的，而不是先把全部输入缓存在内存里。

### 4. Finalize

解析结束后，命令会从“事件摄取”切换到“结果组装”。BinlogViz 会在这一阶段完成依赖完整输入窗口的输出，例如 Top-N 风格报告章节以及其他 finalize 阶段的聚合工作。

命令会在进入这一步之前打印最终组装状态消息，帮助操作者区分“解析进度”和“结果组装”两个阶段。

### 5. Render

当 `Finalize()` 返回完整的分析结果后，渲染器会把文本或 JSON 输出写到标准输出。渲染阶段与解析和分析阶段刻意分离，这样用户可见的输出格式才能保持清晰、稳定和可预期。

## 流式命令路径

命令路径刻意保持流式：

1. 解析输入文件。
2. 校验文件存在。
3. 创建命令拥有的临时 DuckDB 存储。
4. 解析事件。
5. 立刻标准化每个事件。
6. 直接把标准化事件传给 `analyzer.Consume`。
7. 在解析完成后调用一次 `Finalize()`。
8. 把最终报告渲染到 `stdout`。

这种设计使 BinlogViz 能处理有序 binlog 范围，而不需要先在内存里构建一个巨大的事件缓冲区。

## 聚合进度行为

当 Parser 支持进度回调时，BinlogViz 会把聚合后的解析进度渲染到 `stderr`。进度基于所有有序输入文件的总大小，而不是每个文件单独显示一个进度指示器，因此操作者看到的是整个输入集的统一进度视图。

解析完成后，BinlogViz 会把解析标记为结束，并在调用 `Finalize()` 之前向 `stderr` 打印 `Finalizing analysis...`。

## 为什么进度和 discovery 输出使用 stderr

BinlogViz 把报告数据保留在 `stdout`，把面向人的状态输出放在 `stderr`。

这种拆分对需要管道或重定向报告的操作者很重要：

- `stdout` 上的文本报告可以安全重定向到文件。
- `stdout` 上的 JSON 报告可以保持机器可消费。
- `stderr` 上的进度更新不会污染文本或 JSON 输出。
- discovery 模式下输出到 `stderr` 的已解析文件列表，可以说明实际分析了什么，而不会污染报告流。

在 discovery 模式下，命令会在分析开始前把解析出的有序 binlog 文件列表打印到 `stderr`。

## 管线中的 DuckDB

DuckDB 是一个临时存储，用来支撑 finalize 阶段的结果组装和受限 SQL 上下文存储，同时又不破坏主命令路径的流式形态。

从架构角度看，核心点很简单：`binlogviz analyze` 每次运行都会创建一个命令拥有的临时 DuckDB 存储，把它传给分析器，并在命令退出时清理掉。

如果你想看生命周期细节、运维侧影响，以及大规模分析时用户可能观察到的现象，请继续阅读 [DuckDB 临时存储](./duckdb-temp-store.zh-CN.md)。
