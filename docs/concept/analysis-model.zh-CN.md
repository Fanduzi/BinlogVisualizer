# 分析模型

本文说明 BinlogViz 如何定义各个报告区块，以及最终分析结果是如何组装出来的。

BinlogViz 不会尝试重建完整的数据库历史。它消费规范化后的行级 binlog 事件，在流式处理中聚合有界的负载信号，并在结束时生成围绕运维问题组织的报告：哪些表写入最多、哪些事务最大、什么时候出现尖峰，以及是否有阈值被触发。

## Workload Summary

`Workload Summary` 是分析结果窗口的顶层汇总。

它包括：

- 总事务数
- 总影响行数
- 总规范化事件数
- 开始时间
- 结束时间
- 持续时长

解读时有几个细节需要注意：

- 时间范围反映的是最终进入分析结果的时间戳，而不是用户主观期待的墙上时钟区间。
- 如果缺少时间戳，不同渲染格式会回退为留空或 `N/A` 一类的表现。
- 持续时长基于分析完成后的摘要起止边界计算，而不是基于用户输入的预期窗口直接显示。

可用这一节回答："我刚分析的这段负载总体有多大？"

## Top Tables

`Top Tables` 按总影响行数对表进行排序。

每个表条目跟踪：

- schema 名称
- table 名称
- 总行数
- insert 行数
- update 行数
- delete 行数
- 触达该表的事务数

这是一个写入活动排名，不是存储大小视角，也不是读查询画像。某个表排得更高，仅表示在分析窗口内它承受了更多行级写入活动。

可用这一节回答："在这段输入范围里，哪些表承受了最多写负载？"

## Top Threads

`Top Threads` 按会话排名，用来回答这个窗口里谁写得最多，而不必手工按事务聚合。

每个会话是一个 `server_id` 上的一个 `thread_id`。只有 binlog 存了 `user@host` 时，才会保留 thread id 为 0 的会话。两者都没有的事务不进入这张表。

有行变更时按行数排序，否则依次按事件数、字节、事务数。`server_id`、`user@host` 和 schema 只在 binlog 带了这些字段时出现。

`--top` 同时限制文本、Markdown、JSON 和 HTML。`--top-threads` 覆盖这个上限。`0` 表示不限制。

可用这一节回答："这个窗口里哪个线程或账号写得最多？"

## Top Transactions

`Top Transactions` 按总影响行数对重建出的事务进行排序。

每个事务条目包括：

- 事务键
- 开始时间
- 结束时间
- 持续时长
- 总影响行数
- 事件数
- 可选的逐表计数
- 可选的逐操作计数
- 取决于 `--sql-context` 的可选 SQL 上下文字段

有几个语义点尤其重要：

- 排名依据是行数，而不是事务时长。
- 持续时长表示重建事务边界之间的时间跨度。
- 事件数表示归属于该事务的规范化事件数，而不是底层解析器原始回调次数。
- 在 JSON 输出里，逐表和逐操作映射仅在非空时出现。

可用这一节回答："哪些单个事务主导了负载，或者看起来运维成本最高？"

## Minute Activity

`Minute Activity` 会把写入活动聚合到按分钟划分的桶中。

每个分钟桶包含：

- 分钟时间戳
- 该分钟内总行数
- 该分钟内事务数
- JSON 输出中可选的逐表行数汇总

这一节用于暴露负载在时间轴上的形状，而不是单个事务详情。它尤其适合观察一段输入范围内何时出现突增、爬升或明显回落。

可用这一节回答："在分析窗口内，写入压力是在哪些分钟升高或降低的？"

## Alerts

`Alerts` 是分析器基于阈值的异常暴露面。

当前告警类型主要围绕：

- `large_transaction`
- `spike`
- `input_format`

`large_transaction` 告警来自分析器选项里的大事务阈值。`spike` 告警只有在启用尖峰检测时才会评估。成功的 MIXED 分析（ROW image 与被忽略的 Query-DML 都大于 0）会追加 `input_format`，让 JSON 消费方知道只统计了 ROW image。

每条告警包括：

- 类型
- 严重级别
- 消息
- 适用时的事务键或分钟时间
- 可选的结构化细节

一个重要的解读规则是：告警来源于分析器阈值和当前可用的聚合上下文。它的目的是提醒运维关注，而不是单独充当根因解释。

可用这一节回答："哪些内容跨过了运维阈值，值得被明确提示？"

## SQL 上下文

BinlogViz 将事务负载指标与可选 SQL 上下文展示明确分离。

`--sql-context` 控制事务查询上下文如何暴露：

- `summary`：当存在查询上下文时，包含一行有界查询摘要和相关元数据。显示被截断时写出原始字节长度
- `off`：所有格式都省略查询文本和 DDL 语句文本。操作、对象和位置仍保留
- `full`：当存在查询上下文时，包含存储后的 SQL 及其元数据。DDL 语句文本同样限制在 4096 字节。截断以 `… [truncated: <shown> of <original> bytes]` 结尾

实现上对 SQL 上下文做了明确限制：

- 存储 SQL 最大为 `4096` 字节。`query_truncated` 表示这个存储上限，不是 160 字符摘要
- 查询摘要的 SQL 正文最大为 `160` 个字符，被截断时后面再加截断标记
- `CREATE`/`ALTER USER`、`GRANT ... IDENTIFIED`、`SET PASSWORD`，以及 MariaDB `IDENTIFIED VIA`/`WITH` … `USING`/`AS`（含 `OR` 插件链）里的口令材料在任何模式下都会先改成 `<secret>`
- `SET PASSWORD` 是 DDL：它会关闭自己的 GTID 组，并出现在 DDL 时间线上

这意味着 SQL 上下文是为了帮助运维快速建立上下文，而不是为了无损归档原始语句。

## 最终结果结构

最终分析结果会被组装为五个稳定的报告区域，再加一个 warning 计数：

- `summary`
- `tables`
- `transactions`
- `minutes`
- `alerts`
- `warnings`

文本输出总是按固定顺序渲染这五个报告区块，即使其中某些区块为空也是如此。JSON 输出总是会发出这些顶层字段；当某类结果不存在时，会使用空数组。

`replica_apply_delay` 是可选的。没有计入的事务同时带上两个 MySQL 8 提交时间戳时省略。它不是空对象，缺失的时间戳也不会被写成延迟 `0`。文本在最忙分钟之后总会有这一节：有非零延迟时是排名，全部相等时是一行，字段不存在时是 `提交时间戳不可用`。

嵌套 JSON 字段则更有选择性。事务级、分钟级和告警详情级的一些可选字段，可能会在源数据为空或不可用时被省略。

这种稳定性是有意设计的：脚本可以稳定消费顶层 JSON 结构，而运维人员也可以依赖文本报告布局在多次运行之间保持一致。
