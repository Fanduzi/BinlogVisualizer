# DuckDB 临时存储

BinlogViz 可以在 `binlogviz analyze` 运行中使用由命令拥有的临时 DuckDB 数据库，但需要传入 `--detail-store duckdb` 标志。从 v0.19.0 起，默认为 `--detail-store none`，即完全不使用 DuckDB。

## 它存什么

从高层看，DuckDB 临时存储会保存 finalize 阶段需要的临时分析数据，包括：

- 用于组装最终报告的已完成或高基数中间结果
- 分析与报告使用的受限 SQL 上下文存储
- 否则会对进程内存造成额外压力的临时结果数据

这个存储只是一次命令执行的内部实现细节，不是用户需要管理的数据库。

## 为什么需要它

从 v0.19.0 起，DuckDB 明细存储需要通过 `--detail-store duckdb` 显式启用。默认的 `--detail-store none` 可以生成等价的 JSON 输出，无需创建 DuckDB 数据库。

BinlogViz 采用的是流式命令路径：parse、normalize、consume，然后 finalize。这种设计很适合分析较大的本地 binlog 范围，但某些报告章节仍然需要一个地方，在完整输入窗口结束前保存或组装中间结果。

DuckDB 的作用包括：

- 降低临时分析数据带来的内存压力
- 在流式消费完成后支持 finalize 阶段聚合
- 保持主解析与消费路径为流式，而不是把全部输入事件都缓存在内存中
- 把受限 SQL 上下文与其他临时分析数据一起放在同一个临时存储中，而不是分散到单独的辅助文件

## 与 `Finalize()` 的关系

`Finalize()` 是流式事件摄取和最终结果组装之间的边界。

在解析过程中，分析器会增量消费标准化事件。解析结束后，`Finalize()` 会读取并组装渲染阶段所需的最终分析结果。DuckDB 临时存储就是这个交接过程的一部分：它保留临时分析状态，使得 Top-N 章节、汇总以及其他依赖完整输入窗口的结果组装可以在所有输入处理完成后再进行。

从操作者视角，可以把这个生命周期理解为：

1. 解析并标准化 binlog 事件。
2. 把事件写入实时 analyzer 状态，以及 DuckDB 支撑的临时分析存储。
3. 调用 `Finalize()`。
4. 构建最终分析结果。
5. 输出文本或 JSON 报告。

## 生命周期与清理

analyze 命令负责整个临时存储的生命周期。

### 创建

分析开始时，命令会创建一个名称形如 `binlogviz-duckdb-*` 的临时目录，并在目录内放置一个 `analysis.duckdb` 文件。

### 使用中

在解析推进期间，以及 `Finalize()` 组装最终结果期间，分析器都会使用这个数据库。

### 清理

命令结束时，清理逻辑会关闭 DuckDB 存储并移除整个临时目录。这意味着无论输出是文本还是 JSON，这个数据库在运行结束后都应该消失。

从操作者角度看，并不存在一个需要长期维护的持久 DuckDB 环境。

## 磁盘与性能影响

DuckDB 临时存储以有用的方式改变了运行时画像，但这些变化在运维层面仍然是可观察的。

### 临时磁盘占用

每次分析都会为 DuckDB 文件占用一些本地临时磁盘空间。对于较大的 binlog 输入，操作者应预期在运行期间会出现一定的临时磁盘增长。

### Finalize 成本

解析本身仍然是流式的，但在较大输入上，finalize 阶段依然可能花费明显时间，因为 BinlogViz 需要在事件摄取结束后组装报告结果。`stderr` 上的 `Finalizing analysis...` 消息，就是这一阶段切换的可见标志。

### 内存权衡

临时存储可以避免把所有临时分析状态都压进 RAM。这通常会改善大输入场景下的表现，但也意味着性能会部分依赖本地磁盘特性。

## 操作者需要记住什么

- DuckDB 是临时的内部工作存储。
- 它的存在是为了支撑流式分析和 finalize 阶段的结果组装。
- 它按每次命令运行创建，并在清理阶段移除。
- 在较大输入下，你可能会观察到临时磁盘占用，以及一个单独的 finalization 阶段。
- 分析完成后，你不需要管理或保留 DuckDB 文件。
