# BinlogViz v0.23.34 发布说明

发布日期：2026-10-13

## 概述

v0.23.34 只改 `binlogviz flashback` 的提示信息，主要是生成列含 `/`、且只在非默认 `div_precision_increment` 下成立时的拒绝消息（#227、#231、#243、#244、#246）。生成的 SQL、退出码和每一个接受/拒绝的判断都与 v0.23.33 相同，`analyze` 输出不变。

对 DBA 来说：

- zh-CN 输出不再夹杂英文前缀：错误以 `错误：` 开头，警告以 `警告：` 开头。
- 手工恢复的说明改正了：先 `SET SESSION div_precision_increment=N`，再 ``FLUSH TABLES `库`.`表` ``，然后 INSERT；同时说明这条 FLUSH 的代价，以及不用 FLUSH 的做法。
- 当真实的增量值是 flashback 无法核对的值时，正确的转储不会再被说成是错的。
- 拒绝时的 stderr 小了约 31%–41%：长段说明每次运行只打印一次，不再每个被拒绝的列都打一遍。

## 变更

- **zh-CN 的错误和警告前缀（#227、#244）**：在 `--lang zh-CN`（或中文 locale）下，错误以 `错误：` 开头，不再是 `Error:`；大小写折叠的警告以 `警告：` 开头，不再是 `warning:`。`window matched 0 events`、`invalid MariaDB GTID` 和「another image with the same inputs」也已翻译（#246）。
- **手工恢复说明（#227、#244、#246）**：MySQL 在打开表时固定生成列表达式，已经打开的表沿用打开时的增量值。现在的说明是：
  - 执行 `SET SESSION div_precision_increment=N`，N 是事故服务器上的值，即该列列出的增量值之一。
  - 再执行 ``FLUSH TABLES `库`.`表` ``（消息里写的是实际表名），然后 INSERT。
  - `FLUSH TABLES` 会等这张表上正在执行的语句结束，期间对这张表的新查询都会排队（线程状态 `Waiting for table flush`）；空闲的未提交事务不会挡住它。繁忙的服务器上请在低峰期执行；也可以不用 FLUSH，改用一个还没访问过这张表的新连接，把 `SET SESSION` 作为第一条语句。
  - 两种做法都在 MySQL 8.0.46 上实测过，恢复出的值正确。
- **说明每次运行只打印一次（#246）**：上面的说明只附在第一条 `div_precision_increment` 拒绝行的末尾，不再每个被拒绝的列都附一遍。每条拒绝仍然是一行 `错误：`/`Error:`，按行解析日志不受影响。大的错误转储上，拒绝的 stderr 小了约 31%–41%。
- **示例 N（#244、#246）**：列出的值里有别的值时，示例跳过 0，并优先取一段连续区间的起点，例如 `0, 28-30` 给 28，`0-3` 给 1。
- **「转储可能没错」的措辞（#231、#243）**：
  - 一个增量值都不成立的被拒绝列，现在直接说「不一致」（#231）。
  - flashback 能核对的增量值都不成立、但有它无法核对的增量值（例如 `10-30`）的列，仍然说转储在这些值下可能没错（#243），之后才是转储错了时的建议。
  - 在 BinlogQA 的 dz193 正确转储上，开发过程中曾有 913 个正确的列被说成转储错了；本版本一个都没有。

## 问题修复

- #227：zh-CN 的拒绝消息以英文 `Error:` 开头，说明里也没有提 `FLUSH TABLES`。
- #231：一个增量值都不成立的错误转储也拿到了 `div_precision_increment` 的措辞。
- #243：真实增量值无法核对的正确转储列，会被说成转储错了。
- #244：N 没有定义，说明里没有 `FLUSH TABLES` 的写法和代价提示，部分 zh-CN 输出仍是英文。
- #246：代价提示误写成 `FLUSH TABLES` 会等未结束的事务；有一处 zh-CN 短语仍是英文；示例 N 可能是 0。

## 验证

- 合并提交上的 CI 和 `go test ./...`（含 MySQL 8.0 和 5.7 上的守卫测试）：通过。
- 离线 flashback 语料（4,898 个用例，en 和 zh），用 BinlogQA 的工具对比 v0.23.33 和之前的 main：
  - 所有脚本逐字节相同，退出码全部一致，接受/拒绝不变。
  - stderr 的每处变化都属于上面列出的提示信息改动。
- `analyze`：1500/1500 相同。
- dz193 以 MySQL 8.0.46 为准核对：被说成转储错了的正确列为 0。
- FLUSH 和新连接两种恢复方式、以及 `Waiting for table flush` 的行为，都在 8.0.46 上实测过。

## 不兼容变更

无。脚本和退出码不变。措辞和前缀有变化：如果按 `Error:` 或 `warning:` 匹配 zh-CN 的 stderr，请同时匹配 `错误：` 和 `警告：`。

## 兼容性

- 支持在 MySQL 5.7 及以上、MariaDB 10.2 及以上执行脚本。
- `flashback` 不连接 MySQL。请先审阅、测试脚本，再连同脚本头在主库的一个新会话里以 `sql_log_bin=1` 执行。某条语句失败时，脚本里之前的事务已经提交。
- JSON `report_version` 仍为 `3`。快照、工作流、产物名称和支持的平台与 v0.23.33 相同。

## 已知问题

完整说明和规避方法见 `docs/concept/limitations.md`。

- flashback 无法区分「增量值无法核对的正确转储」和「错误的转储」，这类列仍会被拒绝，并使用「可能没错」的措辞。
- 需要超过 30 位小数的 `/` 仍然无法核对。
- 在 MySQL 5.7 上，写成 `1e2` 的 JSON 数字显示为 `100.0`，少数这类列会被拒绝，这是安全的一侧。
- 在解析的 binlog 范围内先新增、再修改或改名的列，仍会让事故时的正确转储报 `reordered ... c, c`（安全的一侧）。
