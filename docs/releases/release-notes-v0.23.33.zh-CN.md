# BinlogViz v0.23.33 发布说明

发布日期：2026-10-13

## 概述

v0.23.33 修复 `binlogviz flashback` 核对生成列时与 MySQL 8.0 不一致的两处（#237、#238）。两处都可能误接受：MySQL 会算出不同的值，flashback 却认为 dump 对得上。现在两处都与 MySQL 一致。更多使用 `DIV`、`%` 或 `MOD` 的 DECIMAL 列现在能核对并留在脚本里。少数以前只是碰巧「核对通过」的列改为无法核对：它们在脚本里被省略并加上守卫，不会被错误接受。另外包含三处输出逐字节不变的内部重构（#234、#235、#236），其中一处修复了 #225 的消息标签。`analyze` 输出与 v0.23.32 相同。

**历史改写。** BinlogViz 的提交历史在 2026-10-12 改写过。此前的提交哈希都变了，旧发布说明、issue 或 QA 报告里引用的哈希可能已经找不到。release tag 已指向改写后的提交，已发布的二进制没有变。请按 tag 或 PR 号查找改动。

## 变更

- **标量上的 JSON `[0]`（#237）**：生成列里对不是数组的 JSON 值取 `->'$.v[0]'`，现在像 MySQL 8.0 一样自动包装：`[0]` 就是值本身，其它下标不存在（NULL）。以前 `[0]` 是 NULL，可能拒绝正确的 dump，也可能接受错误的 dump。实际上这类列大多会报告为无法核对，而不是核对通过，这是安全的一侧。
- **`DIV`、`%`、`MOD` 下按 MySQL 舍入（#238）**：`(a / b) DIV c`、`(a / b) % c` 这类 DECIMAL 表达式里，每个 `/` 现在保留 MySQL 的舍入。以前按精确值计算，极少数情况下会接受 MySQL 不会算出的值。规则与 MySQL 一致：
  - 除数为 0 时结果为 NULL。
  - 结果为 0 时 scale 为 0。
  - `DIV` 向零截断。
  - 商超出 BIGINT 时不作判断。
- **更多列能核对**：以前因「未核对」而从脚本里省略的、带 `(a DIV b)` 或 `%` 的 DECIMAL 列，现在会对照记下的值核对并保留。离线语料里有 4 个用例现在生成完整脚本，不再是带守卫的部分脚本。在 MySQL 8.0.46 上用这些脚本恢复，结果与事故前的行一致。
- **重构，输出不变**：schema 目录（#234，ADR-0005）、apply 守卫合成一个模块（#235，ADR-0006）、生成列只用一个表达式求值器（#236，ADR-0007）。脚本、守卫 SQL 和消息逐字节不变，下面的 #225 修复除外。

## 问题修复

- #225：大小写折叠匹配到的表被拒绝时，中文消息里也会写出 schema 文件中的表名，而且每张被拒绝的表都写，不只第一张。
- #237：对非数组 JSON 值取 `$.v[0]` 得到 NULL，MySQL 返回值本身。
- #238：DECIMAL 上 `DIV`、`%`、`MOD` 里的 `/` 按精确值计算，没有按 MySQL 舍入，极少数情况下会误接受。

## 验证

- 合并提交上的 CI、`go test ./...`（守卫测试在 MySQL 8.0 和 5.7 上）、全新 MySQL 8.0.46 上的 MySQL 8.0 端到端测试：通过。
- BinlogQA 模糊测试语料：50 万个用例、约 180 万次探测，以 MySQL 8.0.46 和 5.7.44 的结果为准。
  - MySQL 8.0 上的错误判定：v0.23.32 有 JSON 误拒 5,943、JSON 误接受 5,943、数值误拒 9、数值误接受 3；v0.23.33 为 **0**。
  - 约 31,800 次数值探测新增为核对正确，约 70 个数值用例改为无法核对。
  - MySQL 5.7：JSON 误接受从 1,267 降到 0。剩下 74 个 JSON 拒绝，都是 5.7 独有的 `1e2` 与 `100.0` 渲染差异。其它计数不变。
  - 没有任何一类出现新的错误判定。
- 离线 flashback 语料（4,898 个用例，中英文）：除上面 4 个用例外，所有脚本与 v0.23.32 逐字节相同；所有用例的退出码一致。
- `analyze`：1500/1500 相同。
- 三处重构合并前都在同样的语料上与当时的 main 对比过（逐字节相同）。

## 不兼容变更

无。部分生成列会在「核对通过」和「无法核对」之间变化，见上文。无法核对的列与以前一样，从脚本中省略并加守卫。

## 兼容性

- apply 支持 MySQL 5.7 及以上、MariaDB 10.2 及以上。
- `flashback` 不连接 MySQL。请先审阅、测试脚本，再在主库上新开一个会话、`sql_log_bin=1`、带脚本头一次性执行。某条语句失败时，脚本里它之前的事务已经提交。
- JSON `report_version` 仍是 `3`。快照、工作流、制品名和支持的平台与 v0.23.32 相同。

## 已知问题

完整说明和变通方法见 `docs/concept/limitations.zh-CN.md`。

- [#227](https://github.com/Fanduzi/BinlogVisualizer/issues/227)（剩余部分）：中文拒绝消息仍以英文 `Error:` 开头，提示里没有提到 `FLUSH TABLES`。
- [#231](https://github.com/Fanduzi/BinlogVisualizer/issues/231)：确实错误的 dump 中，对不上任何增量的列常常得到 `div_precision_increment` 的措辞，而不是明确的「dump 不对」。仍会被拒绝。
- MySQL 5.7 上写成 `1e2` 的 JSON 数字渲染为 `100.0`，少数这类列会被拒绝。这是安全的一侧。
- 需要超过 30 位小数的 `/` 仍然无法核对。
- 大小写折叠、在解析的 binlog 内对列做 `MODIFY`/`RENAME`、`--schema-file-db` 头部警告、未知生成列、apply 失败后续跑，与 v0.23.32 相同。
