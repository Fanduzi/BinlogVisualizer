# BinlogViz v0.23.32 发布说明

发布日期：2026-10-12

## 概述

v0.23.32 让 `binlogviz flashback` 的 `div_precision_increment` 提示（#193）重新变快，并让它给出的增量如实可信（#226，以及 #227 的一部分）。在一个 19.5 MB、186 张表、schema 文件被拒绝的 binlog 上，运行耗时 27.2 秒，v0.23.29 为 407.7 秒，v0.23.30 和 v0.23.31 约 10 小时。提示现在还会写出无法核对的增量，而不是给出不完整的范围或干脆不给。哪些列和表被接受或拒绝没有变化，脚本也都不变。`analyze` 与 v0.23.31 相同。

## 变更

- **被拒绝的运行更快（#226）**：含 `/` 的生成列被拒绝时，提示会在 `div_precision_increment` 0 到 30 下逐个重新核对。现在每张表的行镜像只解析一次，由这张表所有生成列和所有增量共用；输入冲突扫描只做一次；示例只在打印时格式化；在上一个增量下不成立的镜像会在下一个增量下最先尝试。内存占用不变。
- **如实的增量列表（#227）**：记下的值没有矛盾、但某些镜像无法计算的增量（商超过 30 位小数、值被截到列的范围），现在作为无法核对的增量写出来，例如「在 div_precision_increment 为 10-27 时成立，为 28-30 时 flashback 无法核对」。没有能核对的增量对得上、但有些增量无法核对时，保留 #193 的措辞和两种解释。以前这些增量被悄悄省略，「只在 10-27」看起来像精确范围，有些列甚至没有提示。
- **建议（#227）**：报错现在建议用 `--exclude-table` 排除这张表（或用 `--include-table` 只列出其他表），中英文一致。

## Bug 修复

- #226：带 #193 提示的被拒绝运行，在大 binlog 上比 v0.23.29 慢很多倍（某个语料上约 10 小时，而不是 7 分钟）。
- #227（部分）：增量范围可能不完整或缺失，`--include-table` 的建议有误导。#227 剩下的部分见「已知问题」。

## 验证

- 合并提交上的 CI（`verify`、`flashback e2e`）、`go test ./...`，以及在全新 MySQL 8.0.46 上跑的 MySQL 8.0 端到端测试：通过。
- 在空闲的 8 核机器上计时，19.5 MB、186 张表的 binlog 加事故当时的转储（被拒绝的运行），3 次取中位数：v0.23.32 **27.2 秒**，v0.23.29 407.7 秒。16 张表的子集：2.9 秒，v0.23.29 为 39.7 秒，v0.23.30 为 107.0 秒，v0.23.31 为 109.7 秒。v0.23.30/31 跑完整 binlog 约 10 小时。完整 binlog 加错误的转储：28.6 秒。峰值内存与 v0.23.29 相差不到 3%。
- 增量列表与真实 MySQL 8.0.46 和 5.7.44 在增量 0–30 下的结果对照，正确转储 4608 个被拒绝的列、错误转储 17154 个：没有把 MySQL 不会产生的增量写成成立，也没有成立的增量同时缺失于「成立」和「无法核对」两个列表。中英文计数相同。
- 判定：被拒绝的列集合与 v0.23.29、v0.23.30 相同（正确转储 4608/4608，错误转储 17154/17154），被接受的脚本与 v0.23.31 逐字节一致。离线 flashback 语料：4897/4897 个用例的 SQL 与 v0.23.31 逐字节一致，只有拒绝信息不同。`analyze`：1500/1500 相同。
- 回归：#187/#215（59 个实测用例）、#167、#192/#208 守卫用例、#183 绕过用例、正确执行和 #180 在 MySQL 8.0 和 5.7 上都与 v0.23.31 一致。

## 破坏性变更

无。只有拒绝信息的文字和速度变化。

## 兼容性说明

- 执行支持 MySQL 5.7 及以上、MariaDB 10.2 及以上。
- `flashback` 从不连接 MySQL。先审阅、测试脚本，再在主库上新开一个会话、`sql_log_bin=1`、带上脚本头执行。某条语句失败时，脚本里更早的事务已经提交。
- JSON `report_version` 仍是 `3`。快照、工作流、产物名和支持的平台与 v0.23.31 相同。

## 已知问题

完整说明和绕过办法见 `docs/concept/limitations.zh-CN.md`。

- [#225](https://github.com/Fanduzi/BinlogVisualizer/issues/225)：被拒绝的折叠表的转储表名标注只在英文报错里有，而且只加在第一张被拒绝的表上。只影响提示：flashback 仍退出 1，不输出 SQL。
- [#227](https://github.com/Fanduzi/BinlogVisualizer/issues/227)（剩余部分）：中文报错仍以英文 `Error:` 开头，提示里也没有提到 `FLUSH TABLES`。
- [#231](https://github.com/Fanduzi/BinlogVisualizer/issues/231)：确实错误的转储里，任何增量都不成立的列现在常常得到 `div_precision_increment` 的措辞（带无法核对的列表），而不是直接说「转储有误」。仍会被拒绝：flashback 退出 1，不输出 SQL。正确转储的拒绝信息也总会列出几个无法核对的增量，通常是 `28-30`。
- 大小写折叠假定全小写的 binlog 表名来自 `lower_case_table_names=1` 或 `2` 的服务器。在同时有 `t` 和 `T` 的 `lower_case_table_names=0` 服务器上，只含 `T` 的转储会被用在 `t` 上；守卫会在任何写入之前停止执行，或 flashback 退出 1。请使用表名与 binlog 完全一致的转储。
- 某一列在解析到的 binlog 里先被加上、之后又在其中被修改或改名（`MODIFY`、`CHANGE`、`RENAME COLUMN`）时，正确的事故当时转储仍会失败，报 `reordered ... c, c`。会安全失败。只解析包含事故的 binlog，或者用这两次 `ALTER` 之间导出的转储。
- `--schema-file-db` 与好几个 `Database:` 头冲突时，警告只写出最后一个冲突的头。
- 脚本不知道的生成列（没有 `--schema-file`，解析到的 binlog 里也没有 `CREATE`）仍会被赋值，执行可能停在 `ERROR 3105`。
- 执行失败后接着跑：保留脚本头（第一个 `-- gtid:` 之前的所有行），只删掉失败块上面的块，在新会话里执行脚本头加上失败块及其后的全部内容。
