# BinlogViz v0.23.27 发布说明

发布日期：2026-10-09

## 概述

v0.23.27 修复 `binlogviz flashback` 守卫报错的截断可能显示一个不存在的列（#208）。以 ` |` 结尾（或以 `| ` 开头）的列名会和真正的分隔符拼成 ` | `，200 字节截断就可能只保留半个列名。现在守卫标签里的每个 `|` 都显示为 `/`。守卫拒绝的情况不变，仍然不写入任何行。`analyze` 的输出和其他 flashback 语句与 v0.23.26 相同。

## 变更

- **守卫标签改写所有 `|`（#208）**：`ERROR 1231` 那一行里，库名、表名、列名中任何位置的 `|` 都显示为 `/`，名字不会再拼出 ` | ` 分隔符，按字节截断总是保留完整的列名。
- 守卫打印到 stdout 的 `SELECT`，以及 SQL 里对 `information_schema` 的检查，仍用真实名字。

## Bug 修复

- #208：列名以 ` |` 结尾时，`ERROR 1231` 那一行可能保留去掉 ` |` 的列名，显示一个不存在的列。#208 的复现现在只保留第一个完整列名（106 字节）。

## 验证

- 合并提交上的 CI、`go test ./...`（含 `TestGuardSafeLabel` 和 `TestGuardErrorValuePipeSuffix`），以及在全新 MySQL 8.0.46 上跑的 MySQL 8.0 端到端测试（含 `TestFlashbackRoundTripMySQL80`）：通过。
- 在 MySQL 8.0.46 和 5.7.44 上跑 13 个含 `|` 的真实用例（#208 复现；`|` 在列名开头、结尾、中间；只有 `|` 的列名；本来就含 `/` 的列名；含 `|` 的中文表名和列名；`|` 跨在截断点上或恰好在截断点），用 `mysql --force` 和遇错继续的执行器：两台服务器上 13/13 与预期一致，不超过 200 字节，合法 UTF-8，行和 GTID 集合不变，之后的写入报 `ERROR 1792`。v0.23.26 为 0/13。
- 20 个 #192 用例在两台服务器上仍然通过，与 v0.23.26 逐字节一致。对截断 SQL 做模糊测试：每种模式、每台服务器 3000 个用例 0 个不一致，包括 ` |` 结尾、`| ` 开头和任意位置含 `|` 的列名。
- 目标不对：每台服务器 21/21 安全。目标正确：每台服务器 6/6 还原一致。#180、#191、#197 的行为与 v0.23.26 相同。
- 列名都不含 `|` 时，生成的脚本与 v0.23.26 逐字节一致。596 个用例的离线 flashback 差异对比没有实际差异，拒绝情况不变。`analyze` 在 1509 个用例上与 v0.23.26 逐字节一致。

## 破坏性变更

无。守卫报错里名字中的 `|` 显示为 `/`。

## 兼容性说明

- 执行支持 MySQL 5.7 及以上、MariaDB 10.2 及以上。
- `flashback` 从不连接 MySQL。先审阅、测试脚本，再在主库上新开一个会话、`sql_log_bin=1`、带上脚本头执行。某条语句失败时，脚本里更早的事务已经提交。
- JSON `report_version` 仍是 `3`。快照、工作流、产物名和支持的平台与 v0.23.26 相同。

## 已知问题

完整说明和绕过办法见 `docs/concept/limitations.zh-CN.md`。

- 守卫报错那一行里，列名中的 `|` 显示为 `/`，所以 `a|b` 和 `a/b` 在那里看起来一样。守卫在 stdout 上的 `SELECT` 和 SQL 里仍是真实列名。
- 目标正确时，块中间重连会让这个块没有应用。在新会话里带上脚本头，从这个块接着执行。
- [#167](https://github.com/Fanduzi/BinlogVisualizer/issues/167)：解析到的 binlog 里的 `ALTER` 会再应用到已经包含它的转储上。拼接的多库转储只用第一个 `Database:` 头。
- [#187](https://github.com/Fanduzi/BinlogVisualizer/issues/187)、[#193](https://github.com/Fanduzi/BinlogVisualizer/issues/193)：带空格的 `Database:` 头和 `lower_case_table_names` 下的大小写混用；非默认 `div_precision_increment` 加 `DECIMAL` 操作数。都会安全失败。
- 脚本不知道的生成列（没有 `--schema-file`，解析到的 binlog 里也没有 `CREATE`）仍会被赋值，执行可能停在 `ERROR 3105`。
- 执行失败后接着跑：保留脚本头（第一个 `-- gtid:` 之前的所有行），只删掉失败块上面的块，在新会话里执行脚本头加上失败块及其后的全部内容。
