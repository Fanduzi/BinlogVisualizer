# BinlogViz v0.23.29 发布说明

发布日期：2026-10-09

## 概述

v0.23.29 修复 `binlogviz flashback --schema-file` 绑定表定义的三种情况（#167）。在 `ADD COLUMN` 之后导出、而这次 `ADD COLUMN` 也在解析到的 binlog 里的正确转储，不再被拒绝。拼接的多份 mysqldump 输出里，每个 `Database:` 头都绑定它后面的那份转储。未带库名的表名有歧义、导致好几张表没有定义时，每一张都会给出警告。新接受的情况在实测中都还原正确，时间线之外的转储仍会被拒绝。`analyze` 的输出与 v0.23.28 相同。

## 变更

- **转储里已经有的 `ADD COLUMN`（#167）**：解析到的 binlog 里的 `ADD COLUMN`，如果这一列已经以相同定义出现在 schema 文件里，就当作已经应用过。以前它会被再应用一次，转储被拒绝，报 `reordered (schema file ...; binlog ...)`，同一列出现两次（`c, c`）。列的类型、长度、字符集、有无符号、生成表达式、小数精度或 `ENUM` 成员不同的转储仍会被拒绝。只差 `NOT NULL`、`DEFAULT` 或排序规则时不影响值，会被接受。
- **拼接的转储（#167）**：每个 mysqldump `-- Host: ... Database:` 头都像 `USE` 一样，为后面那份转储设定库名。以前只用第一个头，后面的转储会绑到错误的库。第一个头之前的内容不绑定，并给出警告。
- **每张没有定义的表都警告（#167）**：未带库名的表名出现在多个库、导致待绑定的定义被丢弃时，每一张没有定义的表都会给出逐表警告，而不是只点名其中一张。

## Bug 修复

- #167：解析到的 binlog 里的 `ALTER` 会再应用到已经包含它的转储上，拼接的转储也只用第一个 `Database:` 头。这两种情况都会拒绝或忽略正确的事故当时转储。

## 验证

- 合并提交上的 CI、`go test ./...`（含四个新的 #167 单元测试），以及在全新 MySQL 8.0.46 上跑的 MySQL 8.0 端到端测试（含 `TestFlashbackRoundTripMySQL80`）：通过。
- 在 MySQL 8.0.46（FULL）和 5.7.44 上跑 34 个 #167 对抗用例，每个脚本都在事故后的状态上执行，再逐行和用 `CHECKSUM TABLE` 比较：v0.23.29 还原 89 个，v0.23.28 为 54 个，这次改动没有造成写错数据。新接受的情况：以 `AFTER` / `FIRST` 加上的普通列、STORED 和 VIRTUAL 生成列，先 `ADD` 再 `DROP`，多张表上的多次 `ALTER`，区间中途导出的转储，以及事故当时的转储。时间线之外的转储、过期转储和定义有变化的转储仍会点名拒绝。
- 169 个脚本里的 561 条撤销语句，逐列与 `mysqlbinlog -vv` 的前镜像一致。
- 各种头顺序、夹杂 `USE` 的拼接转储现在都能还原，v0.23.28 会拒绝。两个版本都退出 0 时，除了每次运行的令牌外 SQL 完全相同（67/67）。
- 回归：#187/#215 的绑定用例除预期的拼接转储变化外不变；#192/#208 守卫用例、#183 绕过用例、#180 以及 8.0 和 5.7 上的正确执行，与 v0.23.28 一致。4898 个用例的离线 flashback 差异对比有 63 处不同，都是预期的 #167 变化。`analyze` 在 1500 个用例上与 v0.23.28 逐字节一致。

## 破坏性变更

无。一些 v0.23.28 拒绝的转储现在会生成脚本，拼接的转储每一段都绑定到自己的 `Database:` 头。

## 兼容性说明

- 执行支持 MySQL 5.7 及以上、MariaDB 10.2 及以上。
- `flashback` 从不连接 MySQL。先审阅、测试脚本，再在主库上新开一个会话、`sql_log_bin=1`、带上脚本头执行。某条语句失败时，脚本里更早的事务已经提交。
- JSON `report_version` 仍是 `3`。快照、工作流、产物名和支持的平台与 v0.23.28 相同。

## 已知问题

完整说明和绕过办法见 `docs/concept/limitations.zh-CN.md`。

- [#193](https://github.com/Fanduzi/BinlogVisualizer/issues/193)：非默认 `div_precision_increment` 加 `DECIMAL` 操作数会被拒绝，报错指向转储。会安全失败。
- [#215](https://github.com/Fanduzi/BinlogVisualizer/issues/215)：大小写匹配假定全小写的 binlog 名字来自 `lower_case_table_names=1` 或 `2` 的服务器。在同时有 `t` 和 `T` 的 `lower_case_table_names=0` 服务器上，只含 `T` 的转储会被用在 `t` 上，守卫在任何写入之前停止执行（或 flashback 退出 1）。折叠后的表被拒绝时，错误里写的是 binlog 表名，也不打印折叠警告。两者都会安全失败。请用表名与 binlog 完全一致的转储。
- 某一列在解析到的 binlog 里先被加上、之后又在其中被修改或改名（`MODIFY`、`CHANGE`、`RENAME COLUMN`）时，正确的事故当时转储仍会失败，报 `reordered ... c, c`。会安全失败。只解析包含事故的 binlog，或者用这两次 `ALTER` 之间导出的转储。
- `--schema-file-db` 与好几个 `Database:` 头冲突时，警告只写出最后一个冲突的头，结尾的「未带库名的表没有使用」也不准确：转储头与 `--schema-file-db` 一致的那一段里的表会被使用。
- 库名首尾都是反引号，或以空格开头时，`Database:` 头会丢掉这个字符，这张表没有定义。
- 守卫报错那一行里，列名中的 `|` 显示为 `/`。守卫在 stdout 上的 `SELECT` 和 SQL 里仍是真实列名。
- 脚本不知道的生成列（没有 `--schema-file`，解析到的 binlog 里也没有 `CREATE`）仍会被赋值，执行可能停在 `ERROR 3105`。
- 执行失败后接着跑：保留脚本头（第一个 `-- gtid:` 之前的所有行），只删掉失败块上面的块，在新会话里执行脚本头加上失败块及其后的全部内容。
