# 编码规范

English: [coding-standards.md](coding-standards.md)

这些规则适用于每一次改动，不管是人写的还是 agent 写的。由 CI 强制的规则都写明了怎么检查。现有的技术债记在一份只能往下调的基线里：旧代码不会挡住新改动，但任何改动都不能让它变得更糟。

## 1. 规模

- **文件：软上限 800 行**，测试文件也算。新文件超过 800 行，CI 失败。已经超限的文件最多比自己的上限多 20 行；文件变小时，上限跟着降下来。需要更多空间时，先把代码搬出去。
- **函数：圈复杂度不超过 40，目标 25 以内。** 测试函数、赋给包级变量的函数字面量都算。已经超过 40 的函数不能再变复杂，加 1 也不行。
- **函数：函数体不超过 150 行，不算只有 `//` 注释的行。** 已经超长的函数不能再变长，加一行也不行。golangci-lint 的 `funlen` 另外限制新函数不超过 100 条语句。测试函数不限长度：表驱动测试本来就长，但复杂度照样算。
- 长流程写成一串阶段：顶层函数每个阶段调用一个函数，每个阶段返回自己的结果或错误。

CI：`codehealth`（文件、复杂度、函数长度），以及 golangci-lint 在改动行上的 `gocyclo`、`funlen`。

## 2. 锁

- **每个临界区只有一个加锁点和一个解锁点。** 把加锁的部分写成单独的函数，开头 `mu.Lock(); defer mu.Unlock()`。
- 不要在每个提前返回的地方解锁。函数必须中途放锁时，就在那里拆开：一个持锁的阶段函数，一个不持锁的。

```go
// 不好：每条退出路径都得记得解锁。
s.mu.Lock()
if err := a(); err != nil {
	s.mu.Unlock()
	return err
}
s.mu.Unlock()
return b()

// 好：一个临界区，一次解锁。
if err := s.lockedA(); err != nil {
	return err
}
return b()

func (s *S) lockedA() error {
	s.mu.Lock()
	defer s.mu.Unlock()
	return a()
}
```

## 3. 注释

- **注释解释为什么**这样写：约束、不变量、它防止的故障。
- **代码里不写 issue 编号、QA 轮次或 ADR 章节历史**（`#123`、`§29.10`、"第 3 轮修复"）。这些历史写进提交信息、PR 或 ADR。读者需要设计背景时，可以写 ADR 的路径（`see docs/adr/0011-....md`）。

CI：`codehealth` 按文件统计 Go 注释里的引用：`#123`、全角 `＃123`、`owner/repo#123`、`PR#123`、`PR 123`、`PR-3`、`issue 123`、`GH-123`、issue 和 PR 的 URL、`§4`、`round 3`。每个文件的数量不能上升，没有引用的文件不能新增。把引用改写成上面另一种写法，数量不会下降。计数器不可能认出所有说法；规则针对的是历史本身，不是写法。

## 4. 不留死代码

- 没用的代码直接删。不要"留着以后用"，不要留注释掉的代码，不要留没人调用的路径。
- **迁移到新路径时，在同一个改动里删掉旧路径**，或者在本 PR 写明的下一个 PR 里删。没有调用方需要时，不加兼容层。

CI：golangci-lint 在改动行上的 `unused`，以及 `deadcode`：每个不可达函数按名字记在基线里，新增一个就失败，并报出函数名和位置。deadcode 不带 `-test` 运行，所以只被测试调用的函数也算死代码。用 `go run ./internal/codehealth/cmd/codehealth deadcode` 列出来。

## 5. 测试断言行为

- 测试检查代码使用者能观察到的东西：输出、返回的错误、存下的状态、发出的事件。
- 行为坏了它要失败，只改实现时它要继续通过。不要断言私有调用顺序，也不要把实现抄进测试。
- 读源码或文档的守卫测试（lint 守卫、文档版本钉）在守卫本身就是目的时可以用；失败信息里写清楚该怎么修。

## 6. README 和文档不堆积

- README 和 landing page 介绍产品：它做什么、怎么安装当前版本、文档在哪。它们不是 changelog。
- 逐版本说明写进 release notes 和升级指南；功能细节写进 `docs/` 下的页面，从 README 链过去。
- README 形状守卫和 `make release-check`（`scripts/check-release-prep.sh`）负责检查。

## 7. 第三次打补丁之前先设计

- **同一块代码 QA 失败两次，就停止打补丁。** 在 `docs/adr/` 下新写或更新一份 ADR：失败的前提、备选方案、决定。评审通过后再实现。
- 同一个函数里补丁摞补丁，说明模型错了，而不是还差一个分支。

## 8. 基线

`internal/codehealth/baseline.json` 给每个超限的文件或函数记一个上限：`files`、`test_files`、`complex_functions`、`test_complex_functions`、`long_functions`、`issue_refs`（按文件）和 `deadcode`（按函数）。没有合计值，一个条目省出来的空间不能挪给另一个条目用。

- `codehealth check` 在这些情况下失败：某个值没有条目；高于上限（文件另加 20 行）；低于上限。最后一种的意思是"跑 `make codehealth-baseline`"：上限跟着债务往下走，省出来的空间以后不能再用。
- `codehealth compare` 和基准提交上的基线比较。已有条目只能变小或消失。新增条目会失败，所以删掉的条目不能再拿来用；别的文件变小了，新的超限文件照样失败。
- **拆分和改名。** 新增条目的唯一办法是作为已有条目的后继：`make codehealth-baseline FROM="internal/x/a.go=internal/x/old.go internal/x/b.go=internal/x/old.go"`。条目会记下 `split_from`，compare 在同一个改动里拿它和原条目核对：所有后继加上原文件或原函数剩下的部分（按当前实测），不能超过原来的上限；每多一个文件可以多 20 行（package 子句和 import），每多一个函数可以多 1 复杂度或 2 行。改名就是拆成一块，没有额外余量。函数的键是 `pkgdir:Recv.Func`，同一个包里给文件改名，函数的键不变。不可达函数不能靠改名进基线，直接删掉。
- **生成文件。** `Code generated ... DO NOT EDIT.` 标记本身什么也豁免不了。只有 `generated_files` 列出了这个路径，并且文件第一行正好是 `// Code generated by <generator>. DO NOT EDIT.`（Go 的正则，只看第一行），这个文件才会被跳过。compare 只接受给基准提交上还不存在的文件新增 `generated_files` 路径。golangci-lint 同样不认标记（`generated: disable`），只跳过列出的路径。目前列表是空的。
- **Go 能编译到的地方都查。** codehealth 检查模块里所有 `.go` 文件，包括 `testdata`、`vendor`、`_` 和 `.` 开头的目录，因为 import 路径能引用到它们。跳过 `.git`、`node_modules` 和嵌套模块。
- **`//nolint`** 必须写明 linter 和理由（`//nolint:errcheck // 理由`），由 `nolintlint` 检查。codehealth 不认 `//nolint`。
- CI 不检查的：锁、注释意图、测试和设计这几条（第 2、3、5、7 节）是评审时的约定。PR 也可以直接改 `.golangci.yml` 或 lint workflow 本身，评审时要看这些改动。

## 检查与命令

| 检查 | 在哪跑 | 什么时候失败 |
| --- | --- | --- |
| golangci-lint（`.golangci.yml`） | `lint` workflow、`make lint` | 改动行上出现新问题：errcheck、govet、staticcheck、ineffassign、unused、misspell、nolintlint、gocyclo > 40、funlen、gofmt、goimports |
| `codehealth check` | `lint` workflow、`make codehealth`，以及 `go test ./...`（`TestRepoWithinBaseline`，不含 deadcode） | 代码和基线对不上：新的超限文件或函数、条目高于上限、条目低于上限、新的 issue 引用、新的不可达函数、`generated_files` 里的路径缺少生成头 |
| `codehealth compare` | `lint` workflow | 基线比基准提交上的宽松：调高了限制、调高了条目、新增条目没有有效的 `split_from`、给已有文件加了 `generated_files` 路径 |

- 还完技术债后，`make codehealth-baseline` 把基线降到当前数字，并记录 `FROM` 里给出的拆分和改名。任何一项要升高它都会拒绝。
- `go run ./internal/codehealth/cmd/codehealth refs` 列出注释里的 issue 引用；`go run ./internal/codehealth/cmd/codehealth deadcode` 列出不可达函数。
- golangci-lint 不带 `--new-from-rev` 运行时才会报改动行以外的已有问题；碰到那段代码时顺手修掉。
